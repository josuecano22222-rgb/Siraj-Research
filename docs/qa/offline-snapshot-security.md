# Offline snapshot components: security review status

**IN PROGRESS — NOT A USABLE OR APPROVED EXPORT.** No endpoint, UI export, key provisioning or persistence is registered. `siraj_research.setup.offline_snapshot` is callable from Python/bench by privileged operators despite not being whitelisted. Do not run it against actual site records or provide keys until a separate security review and explicit authorization. The viewer accepts visibly UNVERIFIED v1 files and an experimental signed v3 format only with an independently supplied trust policy; it cannot consume this module's v2 envelope. See `signed-snapshot-prototype.md`.

## Implemented candidate collector

`collect_current_user` and `issue_current_user` use the current Frappe session, reject Guest, consult DocType read **and export** permissions, use permission-filtered lists and per-document read/export checks. Person, Institution, Place and Source identifiers only are included; Relationships are returned only if the relationship itself and both endpoint nodes pass these checks. Relationship type, labels, linked details, coordinates, child tables, attachments and evidence are deliberately omitted. Both Event identities are excluded while the collision is unresolved. Missing permissions/types are indicated in scope; raw scan caps fail rather than silently truncate. It requests at most 2,001 list rows per allowed type, plus 4,001 Relationship rows, and has a final 2,000-node/2 MiB envelope limit; these caps do not bound database cost, hook cost or server work. Pagination and concurrent writes can produce an inconsistent result. Node/relationship access is **not** proved by the stubs; actual field, share, owner, query hook, export and local customization behavior still needs review and tests.

## Versioned server-side MAC prototype

`issue_current_user` binds a version-2 envelope to the current site/user, UTC creation and expiry (maximum seven days) and a scoped payload. `verify` checks an HMAC-SHA256 over canonical Python JSON, expected site/user, time and expiry. A test secret is supplied in synthetic tests; no key is generated, stored, configured or logged by this module. A secret must be high-entropy, isolated, rotated and protected by an independently reviewed key-management design. An HMAC proves possession of the **shared secret**, not who authorized a record; anyone with that key can forge files. Do **not** distribute this key to a browser/device for verification. The HMAC module itself has no offline verifier, identity/device binding, encryption, trusted offline clock, revocation, or actual current-permission recheck. A separate v3 asymmetric prototype is described in `signed-snapshot-prototype.md`. A MAC-valid payload can still be stale, overbroad, forged by a key holder, or generated by flawed permission code. `verify` is not a payload schema validator and accepts context supplied by its trusted caller; an eventual server must derive context from an authenticated session. Expiry blocks this verifier after its time limit but cannot delete or revoke an already copied file. Do not convert a v2 envelope to the unverified v1 viewer format and claim it is verified.

Before production use, establish a threat model, independent issuer identity and key trust distribution (likely asymmetric verification), authenticated user/device access and encrypted at-rest storage with key lifecycle, offline clock/expiry handling, revocation limitations, snapshot schema and size validation, request throttles and audit privacy. Require real role/share/field/query-hook and cross-user tests, non-atomic scan policy, lifecycle and incident response. A secure sync protocol, server-side reauthorization, version-based conflict handling and adversarial tests are a later stage and do not exist here. No actual record export or real-site security testing has occurred.
