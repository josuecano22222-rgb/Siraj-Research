# Coordinate migration: audit and safety plan

**Status: IN PROGRESS / BLOCKED for implementation and real database verification.** There is no safe migration patch or executed migration yet. The working-tree Data JSON changes are an unreleased prototype, not a migration or permission to run `bench migrate`. The Event collision and four missing legacy patches must be addressed first. This plan is not production execution authorization.

## Current and target schema

The committed SIRAJ `Person`, `Institution`, `Place`, `Event`, `Military Unit` and `Operational Deployment` metadata define separate `latitude` and `longitude` Float fields, generally with precision 6. Confirm actual field definitions, SQL column types/defaults/nullability, customization and data on the target; metadata alone does not prove the physical schema. The requested target keeps these two fieldnames as text (Data) so newly entered decimal strings are not rounded at storage. The form picker supports writable text fields but only previews Float; Explorer parses decimal text and accepts Arabic/Persian digits. Values plotted by browsers are numerical approximations. Child rows and unrelated apps' fields are outside the six-pair prototype. Historical binary/decimal Float precision that was lost cannot be restored.

WGS84-style decimal degrees are assumed (latitude ±90, longitude ±180); web tile display uses Web Mercator latitude approximately ±85.0511. Order is latitude then longitude in forms, longitude then latitude in GeoJSON. Blank, partial, invalid, out-of-range and `(0,0)` values must remain distinguishable and never be silently converted or discarded. Explorer currently suppresses `(0,0)` because old Float defaults can mean unset; a real origin point must not be silently classified as missing without an approved per-record policy. Define server-side validation, text maximum length and handling of existing invalid strings before any release.

## Read-only diagnostic prototype

`siraj_research.setup.coordinate_audit.inspect_coordinate_migration` is a **non-whitelisted** bench-only administrative function: it examines fixed legacy DocTypes/metadata, physical column types via `information_schema` on MariaDB/Postgres, and aggregate pair validity counts via privileged paged reads. It does not return record IDs, coordinate values or default values, and contains no writes. Category counters overlap: invalid counters can overlap incomplete; zero pairs are a subset of complete-valid. Exact zero of numeric fields remains ambiguous. Unsupported databases and missing fields are reported without scanning.

It has only fake-Frappe tests and must first be validated in an authorized isolated environment; it has **not been run on `frappe.com`**. It can scan every row and counts/schema may themselves be sensitive. Concurrent writes mean the result is not a consistent snapshot. Do not run it on production without separate operational approval, load review, correct site verification, and protection of the output. Passing a preflight is not authorization for migration.

## Proposed migration and recovery gates

1. Inventory app versions, field/column types, defaults, custom fields/property setters, constraints, downstream APIs, reports, scripts, external clients, unique combinations and legacy values. Inventory `Event` under both identities only after the Event split design is decided. Preserve all link relationships and identify any duplicate coordinates, which may be legitimate, rather than deduplicating.
2. Establish a fresh backup of database, config, keys, public/private files and app versions; restore it in an approved isolated environment and verify application behavior, checksums and recovery time. The previously reported backup has not been restored.
3. Design and test a version-specific migration that preserves an independently verifiable typed copy of each original value, including null/default state and source identity, before changing storage. Establish exact deterministic numeric-to-text conversion, handling of ambiguous/partial/invalid values, collision checks for backup/shadow field names, idempotence, timeouts, permissions and error handling. Do not use a global DocType rename or rely on transaction rollback of DDL. Do not rely only on cached DocType metadata for the real physical type. Determine how Frappe patches and schema sync interact before writing the patch.
4. Stop writes/jobs/integrations during the approved maintenance window; perform before/after aggregate and detailed restricted comparisons in the rehearsal. Test invalid, empty, one-sided, zero, Unicode-digit and high-precision new coordinates; direct APIs, forms, lists, geographic views, reports and users with differing field permissions. Confirm indexes, schema/defaults, record counts and all links.
5. Rollback must account for **new or edited text coordinates after migration**: Float may lose precision or be unable to represent invalid text. Freeze writes, retain/export those changes securely, and explicitly reconcile before restoring the verified database/files/config backup. A whole-site restore rolls back unrelated app changes after the backup; obtain separate approval and recovery window. Do not offer an in-place reverse cast as lossless. Rehearse restoration and forward recovery before production.
6. Only after written acceptance of the rehearsal, resolved Event/patch dependencies, explicit migration authorization, a fresh verified backup and controlled downtime should an operator follow a separately reviewed runbook. No production commands are authorized here.

## Fixture-only transition model

`coordinate_transition.py` implements a pure candidate conversion and reversible whole-snapshot rehearsal for the six **legacy** DocTypes. It assumes WGS84 decimal degrees, latitude first, longitude second; GeoJSON consumers conventionally reverse the order. Canonical output is ASCII fixed-point decimal text, at most 140 characters, without rounding; leading/trailing zero formatting is normalized. Numeric legacy floats use Python's shortest round-trip representation: this preserves the observed Python float value, not precision previously lost by the database. Original typed values and all supplied other fields, including provenance, are retained in the protected before-state. No CRS can be deduced from a pair; its source must be reviewed separately. Field length and format are proposed and not deployed.

The audit reports invalid, partial, missing, out-of-range and unreviewed-orientation cases. Even apparently valid pairs require explicit `lat_lon` or `swap`; `(0,0)` additionally requires an explicit preserve decision. Both blank values stay unchanged. No swap is inferred, no invalid input silently discarded, and proposals never change the input. The in-memory manifest supports idempotent repeat projection/reversal for exact before/after snapshots, rejecting partial operations, concurrent modifications, additional/missing records and mismatched journals. A manifest must be confidential and trusted; no cryptographic integrity or actual database executor exists. This model does not address shadow columns, physical schema, Event ownership, installed customizations, DDL, concurrent writers or whole-site restore. `execution_ready` remains false.

For an **explicitly authorized isolated copy only**, the existing aggregate audit can be invoked after verifying the correct site, impact and hook behavior (replace the site placeholder with its real isolated-site name):

```bash
bench --site <isolated-site> execute siraj_research.setup.coordinate_audit.inspect_coordinate_migration
```

This diagnostic is non-whitelisted and only requests aggregate/schema output, but is privileged and may scan every row. `bench execute` can commit effects from custom hooks and output may be sensitive; it is not a transactionally consistent snapshot or a guarantee of no side effects. Do not run against the working/production site or share output without review. It has not been tested against the owner's Frappe site. No command for actual conversion is implemented or authorized.

### Shared parsing integration

`utils/coordinates.py` supplies exact Decimal parsing to the fixture transition model, read-only aggregate audit and online Explorer map rendering; the latter converts to binary floats only after exact bounds validation. Desk picker JavaScript still has an independent implementation, now explicitly accepts legacy numeric exponent notation (but not exponent strings) and warns that `(0,0)` may be unset; its existing text-entry precision and read-only Float behavior are retained. Explorer intentionally excludes the ambiguous zero pair. This is partial application integration, not end-to-end consistency: DocType schema/validators, import/export paths, offline record coordinates and migration executor remain unchanged. Metadata and existing values must not be changed without an approved migration/recovery design. Candidate canonical output is ASCII, latitude then longitude, WGS84 assumed, maximum 140 characters without rounding; GeoJSON uses longitude first. Rendering is approximate and historical Float loss cannot be restored.
