# Event identity transition: design and release gates

**Status: superseded.** The transition planned below was superseded by the
`Siraj Event` decision in `docs/decisions/2026-11-siraj-fixes.md`: `Siraj
Event` is now the single SIRAJ event DocType, the former SIRAJ event DocType
was deleted via a guarded patch, and Frappe's core `Event` calendar identity
is untouched. The plan below is preserved for history; it was never executed.

**Status: design/inventory only, not an executable migration.** Do not run `bench migrate`, reload Event metadata, rename/delete DocTypes, seed or disable hooks as a consequence of this document. The local prototype is not in this delivery. The expanded inventory below is mock-tested only; any execution needs separate approval.

## Why this happens and intended ownership

Frappe DocType identities are global within a site. Both Frappe's calendar and this app registered the exact identity `Event`; a module label does not namespace it. The owner observed `Event` module `Siraj Research`, SIRAJ metadata and no Event rows on the test date. Calendar columns remained physically present, but calendar fields were absent in effective metadata. Frappe 15.126.1's Google Calendar insert hook expects `sync_with_google_calendar`; the attempted fixture failed there. ERPNext 15.125.0 also supplies an Event `after_insert` integration expecting calendar participants. In addition, Frappe's Event query and document permission hooks assume calendar `event_type`, owner and participants. SIRAJ's similarly named `event_type` has different semantics. Administrator bypass is not evidence these hooks work for other users.

The **Frappe framework** should own the global `Event` calendar identity; historical research events should use a distinct global SIRAJ DocType (the identity ultimately shipped as `Siraj Event`). The new name was not yet accepted as collision-free on the actual site at the time. A global Frappe rename is not safe: it could rewrite references intended for the calendar. Adding missing fields or disabling hooks is not equivalent to restoring Frappe's controller, metadata, permissions and integrations.

## Potentially affected material and decision points

Inventory Event table and columns, effective and physical schemas, rows, child rows and all installed apps/custom DocTypes, custom fields, property setters, custom permissions, workflows, reports/charts/cards/workspaces, scripts, background jobs, integrations and APIs. Review direct Links, Dynamic Link type/value pairs, ownership/shares, attachments, comments, assignments, versions, audit history, notifications, calendar participants and external identifiers/consumers. Back up app code, configuration, keys, database and public/private files. Fixed reference counts previously reported zero, but only at one time and for a limited list. They do not classify ownership or rule out external or hidden references, changes since the check, or side effects of the earlier failed fixture.

For each record and reference, a site owner must approve a deterministic classification as calendar, research, or **ambiguous**; an ambiguous/unrecognized state stops migration rather than defaulting to either owner. Decide explicitly how to handle overlapping names, missing targets, active calendar integrations, customizations, audit data and consumers. No conversion rules for populated/mixed cases have yet been approved; implementation must not silently drop, overwrite, reparent or reclassify anything. Empty-table evidence is not a universal migration strategy.

## Proposed transition, not execution commands

1. Record exact site versions, effective hooks and customization inventory; approve identity, policies, mapping and compatibility/deprecation strategy for external clients. Produce an expected per-type source/target manifest with integrity checks and restricted access.
2. Freshly back up and independently restore the whole site on an approved isolated copy; document recovery point, files, app revisions, keys, database version, validation and downtime. The 2026-11-15 backup has not been restore-tested.
3. Implement a version-specific, fail-closed transition that creates the new research schema, preserves original values/IDs and approved references, restores the matching Frappe core Event metadata/controller without global rename, reconciles reviewed customizations, and updates SIRAJ consumers. Require checks for unexpected existing target schema/rows, collisions, unknown references, incomplete mappings and repeated runs. Prove the actual mechanics and ordering: in Frappe v15 `before_migrate` precedes pre-model patches and schema sync, followed by post-model patches and orphan cleanup. DDL can commit outside transaction rollback. No safe transition patch or rollback implementation is currently published.
4. Freeze writes, jobs and external integrations for a separately approved maintenance window. Compare pre/post restricted manifests, schema, counts, relationships, permissions and app behavior; abort on any mismatch. No automatic approval based on zero counts.
5. Rehearse complete recovery from the verified pre-change backup, including matching application versions and files/config. A whole-site restore also discards unrelated writes after that backup: freeze writes and preserve/reconcile any post-backup changes under an explicitly approved recovery plan. Test repeat execution and recovery after interrupted DDL; do not assume SQL rollback is sufficient.

## Rehearsal and acceptance matrix

On approved isolated restored copies, test clean install; empty legacy Event; populated research; calendar data; mixed and ambiguous references; conflicting new DocType/record names; custom fields, workflow, permissions and hooks; missing patches; repeated and interrupted runs. Validate record contents, direct/dynamic links, children, files, audit records and external integrations without publishing sensitive values. Check core Event calendar create/read/update/delete, private/public/owner/participant permissions, ERPNext CRM participants and (only with separately controlled credentials) Google sync. Check SIRAJ research event create/read/update/delete, links, Explorer, reports, cards, charts and roles. Test real endpoint denials, field-level permissions and recovery, with actual Frappe versions. A destructive lifecycle test is permitted only in an explicitly authorized isolated environment. Owner sign-off on evidence and a separate maintenance authorization are mandatory before production.

## Additional metadata inventory (optional, NOT YET RUN)

`bench --site frappe.com execute siraj_research.setup.event_reference_inventory.inspect_metadata_event_references`

This non-whitelisted administrative function only counts metadata-defined direct Link fields to Event and possible type selectors across non-single, non-virtual SQL DocTypes. It returns a count of successfully checked fields, nonzero counts and skipped/unknown fields, not row IDs or contents; selectors can be set without a target, counts can overlap, and zero counts are omitted. Singles, virtual DocTypes, standard child `parenttype` columns not declared as fields, free text, code, unmodeled tables and external systems may be missed. It may scan many tables and issue many count queries, and concurrent writes can make results inconsistent. It has only fake-Frappe tests. Use an authorized isolated copy first, with a load window and protected output; `bench execute` commits successful transactions, and custom code/hooks could have side effects. Do not run this command on the working site without separate approval and risk review. Capture the first sanitized error and stop on failure; Frappe bench execute may attempt an exception fallback. Even a clean result is not permission to migrate.
