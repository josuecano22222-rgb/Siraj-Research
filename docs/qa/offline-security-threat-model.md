# Offline record snapshots: threat model and implementation gates

**Decision: not approved for real-record export.** This is a proposed security design and risk register, not a claim of production readiness. No export endpoint, key provisioning, trust-policy delivery, encryption or synchronization is enabled. The v3 signature prototype and v1 unverified viewer have only fixture evidence. The owner must separately approve any real-data tests; no keys or actual records are requested in chat.

## Boundaries, assets and assumptions

Protect record identifiers, relationships, site/user identity, snapshot contents, issuer private keys, device decryption secrets, trust policy and audit logs. Boundaries: authenticated Frappe session → permission-filtered exporter → signed/encrypted file → potentially untrusted transfer/storage → offline viewer/device. Potential attackers include an unauthorized site user, another device user, a network/storage attacker, a malicious snapshot or policy supplier, and a party with an old valid copy. An attacker controlling the issuer, device/browser, viewer code, trusted policy or signing key can defeat the corresponding trust boundary; signatures do not protect against a compromised authorized issuer. Frappe hooks/customizations may have side effects or implement stricter rules than the prototype. No guarantee is made that the device clock, offline user identity, stored file or current permissions are trustworthy.

## Current format versus proposed production format

The v3 **prototype** signs `b'SIRAJ-OFFLINE-SNAPSHOT-V3\x00'` followed by the exact Python-generated UTF-8 JSON body bytes; envelope fields are `version`, unpadded base64url `body`, and unpadded base64url `signature`. Body JSON is serialized by Python with sorted keys, compact separators, ASCII escaping and no NaN; consumers verify the original decoded bytes, not a reserialized object. P-256 ECDSA/SHA-256 signatures are converted from Python cryptography's DER `(r,s)` to 64-byte `r || s` for WebCrypto. Signed body binds site, subject, key ID, random snapshot ID, UTC creation/expiry, scoped nodes and edges. The prototype allows at most seven days. It is **not** a standardized cross-language canonical-JSON profile: define normative byte encoding, duplicate-key handling, Unicode and conformance vectors before an independently implemented issuer is trusted. Python-to-Node WebCrypto fixtures passed locally and in the owner's reported bench environment; actual browser/platform support still requires approved testing.

A production format must define an independent version, strict maximum sizes/depth, explicit schema and operation list, signed content and algorithm identifiers, exact time rules, context/audience/device binding and completeness semantics. Reject unknown versions/algorithms, duplicate JSON keys, malformed UTF-8/base64, overlong inputs, inconsistent scope and truncated downloads. No automatic downgrade to an unsigned format. Current v3 shape/schema checks and file-size bounds are partial; lists are permission-filtered but scans are non-atomic, excluded types/fields are not represented as complete, and Event is excluded. Version changes require reviewed migration/interoperability vectors and rollback-resistant policy distribution.

## Threats, present handling and remaining work

| Threat | Current prototype | Required before actual export |
| --- | --- | --- |
| Hidden records, linked endpoints, field restrictions, ownership or shares | Collector checks current-session DocType/document read and export plus `get_list`; relationships require two visible nodes; only names exported. Event excluded. Stub tests only. | Review effective site hooks/permissions/custom fields and test real non-admin roles, shares, query/document disagreement and direct APIs. Decide if non-atomic scans can be used and fail closed on any scope or permission uncertainty. |
| File modification, partial download, substitution | v3 verifies P-256 signature over original body against independently configured key, exact site/subject/key context, then validates viewer data. Invalid/unknown/expired/revoked inputs are rejected. | Protected, independently authenticated trust distribution and key identity; strict parser and cross-language/adversarial vectors. A public key in the same attacker-controlled file is not a trust anchor. |
| Unsigned/legacy downgrade | v1 can be opened only in a prominently UNVERIFIED path; it cannot enter the signed branch, and its untrusted date is not echoed into the trust-status message. | Product decision whether to disable unsigned files entirely for sensitive use; verify UI state switching and downgrade attacks on supported browsers. |
| Key compromise/rotation | One locally supplied public key/key ID and explicit local revoked lists; no distribution or update mechanism. | Offline-root or hardware-protected issuer, audited restricted online signing, short-lived operational keys, approved key generation and independently authenticated, versioned policy with monotonic anti-rollback, key overlap/retirement and recovery procedures. Stop issuance, revoke compromised key, rotate, securely distribute new policy, invalidate/reissue snapshots and investigate scope. Old offline devices/copies cannot be remotely made safe. |
| Expired/replayed/stale snapshot | Viewer checks signed UTC expiry, issue time, maximum seven-day interval and configured revocation-policy freshness using device clock; hides open signed data after deadline when clock behaves normally. | Agree risk-based validity and renewal; policy version and anti-rollback plus trustworthy time where possible. Offline beyond freshness/expiry must fail closed rather than silently extend. Device clock rollback and files read outside the viewer defeat UI-only expiry. |
| Unauthorized physical/device access and copied files | No encryption. v3 and v1 files are plaintext; owner label is signed context, not local user authentication. | Design reviewed authenticated encryption, encryption-key derivation/wrapping, device/owner authentication, secure storage and recovery, rate-limited unlocking where applicable and malware/backup risk. Sign-then-encrypt ordering, algorithms and metadata leakage need cryptographic review. No proposed protection prevents an authorized user copying plaintext. |
| Browser storage, transfer, deletion | Viewer uses in-memory file input and does not intentionally persist records; browsers/OS, downloads, swap, backups, crash reports and file transfer can still retain copies. | Managed device controls, encrypted transfer/storage, retention policy, secure cleanup procedures and explicit warnings. Closing a viewer does not erase source files, caches, backups or previously copied plaintext; secure deletion cannot be guaranteed on SSD/cloud systems. |
| Stale permission, account disabled, access revoked | Signature only attests issuer key signed a historical payload; offline viewer has no connection to Frappe. | Short validity, current server reauthorization at issuance and on reconnect, device controls and explicit historical-time UI. Permission revocation cannot erase already copied data. Never describe a signature as current authorization. |
| Policy rollback/substitution | Locally configured trust object can be replaced together with viewer files; current policy has no signed version or anti-rollback. | Independently authenticated policy, protected viewer/code delivery, key rotation/recovery and anti-rollback design; manage trust root separately from snapshot and device user. |
| Malicious viewer/code or script injection | Record fields rendered with DOM `textContent`, limits and schema; browser fixtures exercise injected markup. | CSP/pack integrity, local-file execution model, dependency provenance and supported-browser tests; local asset tampering remains fatal unless separately protected. |
| Synchronization or conflicting edits | Not implemented; viewer read-only. | Separate protocol: authenticated server, per-record current read/write checks, version/ETag comparison, conflict reporting and explicit merge policy; no automatic last-write-wins. Review independently before enabling. |

## Proposed implementation and acceptance sequence

1. Freeze schema and trust policy: formal signed envelope, parser/resource limits, version and canonicalization vectors; require security review of cryptographic construction and no unauthenticated downgrade.
2. Implement controlled issuer with session-derived site/user and explicit export permission, reviewed per-field/linked permission semantics, throttles, protected signing key, no sensitive logs, non-atomic-scan strategy and fail-closed errors. Real endpoint stays disabled until independently approved.
3. Design and separately implement authenticated encryption/key wrapping, device/identity controls, versioned independently authenticated trust/revocation policies, recovery and clock policy. Test compromise, rollback, stale and offline recovery scenarios without actual production secrets.
4. On an explicitly authorized isolated environment, test allowed/denied/shared/owned/query-hidden/field-hidden cases and direct APIs, record integrity, revoked/wrong/unknown/expired/substituted/truncated files and cross-user/device attempts. Use appropriately protected data, not samples on the working site. Verify site versions and custom hooks; record sanitized pass/fail evidence.
5. Threat-model synchronization separately. Only after independent review, real isolated results, operational approval, data minimization and device/retention policies should an owner consider a separately authorized real-data test.
