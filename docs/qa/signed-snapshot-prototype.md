# Signed offline snapshot prototype — security gates

**Fixture-tested prototype, NOT approved for real data or production use.** No HTTP/export endpoint, private key provisioning, trusted policy distribution, encryption, sync or real-site test has been implemented. Do not provision keys, enable exports, or construct real record files until security review and separate authorization. Pushing this code is not authorization.

## Connected prototype

`offline_signed_snapshot.issue_current_user` is non-whitelisted and receives an in-memory P-256 private key from a trusted caller. It calls the existing current-session permission collector, binds site, session subject, key identifier, random snapshot ID, UTC issue/expiry and scope to the payload, signs the exact canonical UTF-8 bytes using ECDSA P-256/SHA-256 with a format-specific domain separator, and returns a v3 envelope. A caller can access it from privileged Python/bench, but no HTTP route, key store or actual download is registered. Never put a private key in a command line, browser, repository or chat. This uses the `cryptography` package (declared by the reviewed Frappe v15 tag); the owner's actual Python environments must be checked, not assumed. The collector's permissions and non-atomic scans have only Frappe-shaped stub tests; see `offline-snapshot-security.md`.

The offline viewer uses WebCrypto to verify v3 envelopes against a **separately provisioned** `window.SIRAJ_OFFLINE_TRUST` policy, never against a public key supplied inside the snapshot. It checks the signature, expected site/subject/key, expiry, future issue time, seven-day maximum lifetime, selected key/snapshot revocation lists and the configured revocation-policy freshness deadline; then validates the minimal record schema and displays owner, timestamps and scope. Missing/invalid trust, signature, schema, context, expired snapshot or stale revocation policy rejects the whole file. It also hides an open signed snapshot on expiry/policy deadline while the browser clock permits. Issuer and WebCrypto interoperate in synthetic tests; an offline Chromium fixture verified search/navigation and rejection. No site keys or records were used.

**There is deliberately no default trust policy or automated policy provisioning.** Existing packages contain no key or records. The independently trusted policy, identity, revocation-list freshness and public key must be established through a separately reviewed protected process. If an attacker can replace the viewer code, assets, trust policy or public key, they can substitute a new issuer and defeat this model. The viewer does not authenticate the local user, recheck Frappe permissions or prove the issuer made the correct authorization decision. A public verification key can safely verify without sharing the private signing key, but signatures do not encrypt; the JSON is readable by anyone with the file. Copied files cannot be remotely erased or reliably revoked while offline; lists only reflect the last separately trusted update. Offline expiry depends on the device clock and can be bypassed outside this viewer. It is not a security boundary against a person with file access.

The existing v1 manual import remains available and is clearly labeled **UNVERIFIED**; it cannot establish origin, permission or integrity. Never convert a v3 file to v1 and call it verified. V2 HMAC envelopes are not accepted by the viewer. There is no actual Frappe export, approved encryption/key lifecycle, identity/device authentication, online reauthorization, conflict handling, sync, trusted time, or tested policy update/revocation channel. Field/record restrictions and Event exclusion remain as documented in the collector; this is not a complete Explorer. Define and review all these controls before any real record use.

For the detailed threat model, key-rotation proposal, recovery and pre-production gates, see `offline-security-threat-model.md`. Fixture results reported by the owner are in `milestone-4cf349b-results.md`. The unsigned viewer status no longer echoes an attacker-controlled date that could imitate the signed status; unsigned inputs still carry an UNVERIFIED label and cannot enter the v3 verification branch.
