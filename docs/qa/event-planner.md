# Event transition planner prototype

`event_transition_plan.prepare_transition` is a pure Python, in-memory candidate planner, **not a migration**, Frappe hook, HTTP endpoint, site inventory or CLI. It does not read or write a site and makes no changes to its input. It rejects unclassified or duplicate event names, target-name collisions, malformed/overlapping reference fields, orphaned targets, and reference classifications inconsistent with the target event. It proposes name-preserving research copies and a change of the type component of reviewed polymorphic reference pairs; calendar entries remain on `Event`. Candidate output can include sensitive identifiers: protect it and do not upload it to Git or share it without review.

Input contract: `events` is a list of exactly `{name, classification}` with classification `research` or `calendar`; `references` contains exactly `{doctype, name, type_field, name_field, type_value, target, classification}` for each manually reviewed Event type/name pair; `existing_target_names` contains existing names for the proposed target DocType. Examples and behavior are in `tests/test_event_transition_plan.py`. Classification must be based on authoritative site evidence, not just name/field values or the earlier aggregate counts. Overlapping fields, unknown target ownership and mismatches stop planning; an empty input only means no input was supplied.

**Critical limitations:** No enumerator guarantees complete inventory. This does not copy record values, transform direct Link fields or metadata, verify real column/field types or effective permissions, update attached children, restore Frappe metadata/controller, persist a journal, verify checksums, handle write concurrency, run DDL, or implement rollback. Other references, customizations, scripts, integrations and external data are not examined. Nothing should consume its candidate changes as executable operations. Research and calendar references may have contextual meanings not resolved by the target's classification. Review every case; do not assume matching classifications establish permission to modify it.

Before an actual migration exists, build and validate a version-specific site inventory and explicit ownership mapping, backup/restore rehearsal, write-freeze, source/target fingerprints, byte/field/child preservation checks, core metadata restoration, context-aware reference conversion and rollback strategy. Any unhandled or changed state must block execution. See `event-transition-plan.md`. Unit tests use invented in-memory strings to exercise logic only; they are not inserted into any Frappe site.

## In-memory snapshot projection prototype

`event_snapshot_projection.project` accepts JSON-shaped, manually supplied rows and reviewed classifications/references, preserves supplied values when creating a candidate research copy, projects type-field changes on listed reference rows, retains original Event rows and returns a sensitive undo journal. The reverse `rollback_projection` refuses if an affected projected row differs and preserves unrelated rows. Tests exercise synthetic ownership, attachments, comments, child parent references, mixed calendar/research and mismatch cases. These are not Frappe Documents or SQL operations; JSON excludes database-specific values such as Decimal and binary data. Full row equality is only equality of supplied fields, not proof of completeness. Journals are unencrypted and unauthenticated in memory and must be trusted; never commit them. No scanner supplies them automatically. Direct links, Event-owned references, ambiguous references, schema/controller restoration, actual Frappe constraints, external systems, transaction/DDL behavior and database rollback remain unimplemented. Do not use this projection as a production migration or perform a site rollback with it.

`inspect_projection` now generates pre-counts and missing/unexpected/changed row identities by recomputing the in-memory expected projection and comparing supplied JSON snapshots. This report may disclose identifiers and must be protected. A match says only that the supplied arrays match this partial model; it does not inspect a real site, prove inventory completeness, restore core Event or establish migration/rollback safety.
