# Explorer integration verification

**Status: IN PROGRESS.** The online implementation has not been verified against actual Frappe records, and the requested full disconnected record Explorer is not implemented. The online Explorer is connected in code; an experimental local viewer can open a separately supplied minimal snapshot, but has no authorized Frappe exporter, record database or synchronization. The word “disconnected” in the earlier status referred to operating without the server, not evidence that the online Explorer has no API connection.

## Trace

`/app/siraj-explorer` Page loads `siraj_explorer.js`. Geography calls `visualization.geographic_data`, relationship graph calls `relationship_data` and optional evidence, Structures calls `structure_data`, and dossier leaves call `record_detail`. These use DocType/field allowlists and `report_access.readable_rows`, which calls Frappe's permission-filtered `get_list` and checks each document. Geographic markers require the record's own valid latitude/longitude; linked Place coordinates are not copied. Existing historical `(0,0)` pairs are intentionally excluded because they may represent Float defaults. The graph returns edges only for readable relationships whose two endpoint records are both visible. Structures counts and grouping depend on visible records and readable fields. See `../siraj-explorer.md` and `../original-feature-parity.md` for behavior, pagination and current limitations.

The working Frappe environment exists locally on the owner's machine but is not directly accessible to the development agent. Real-environment testing must therefore be coordinated with the owner. No actual site data, linked-record completeness, Page routing, permissions or network/API failures were inspected by the agent. Earlier operator diagnostics found zero Events in a limited point-in-time check; they do not describe the rest of the registry. Do not insert samples to populate a display. Legitimate records must be created through normal authorized Frappe forms/import processes, respecting required fields, link targets, workflow and permissions; obtain the precise effective metadata on the actual site before giving field-specific import instructions.

## Verification required

Using authorized accounts and existing legitimate records, compare list/document counts and readable fields with every Explorer API and visual view; test private/owned/shared/user-permission records, inaccessible relationship endpoints and linked fields, search, filters, centering, navigation, dossiers, empty/missing data, non-existent/deleted links, field restrictions, failed APIs and localized UI. Capture sanitized requests, assertions, actual results and revision. Include a deliberate negative test via direct API, not only hidden UI controls. Where data is missing, report types and approved ingestion procedure; never fabricate it.

Offline record snapshots require a separate design for field/document permissions at export, minimum scope, sensitive data encryption and device access, consent, lifecycle/expiry, revocation limitations, conflict resolution and reconciliation. The current basemap ZIP contains no records; it is not a disconnected record Explorer and cannot meet that requirement.

## Disconnected-record design gate

A candidate first release is an explicit, read-only, user-initiated export containing only records and fields authorized for that user at export time, with relationships only when both endpoints and applicable linked values are eligible. The pack must identify generation time, scope, version and license/attribution; show offline staleness clearly and never imply live permissions or current data. It must not sync edits or merge conflicts. Offline copies cannot be remotely revoked once copied; expiry in the UI cannot enforce deletion. Portable browser files are not inherently encrypted and encryption would need a separately reviewed design and key lifecycle, so do not export sensitive records in the current basemap-only ZIP. Define threat model, export minimization, encryption/key management, device access, retention, role changes, safety limits and consent before implementation. Existing online API snapshots have outstanding linked-field/derived-label security findings, so reusing them without review is unsafe. Test no network, missing tiles, corrupted/tampered packs, unauthorized fields/links and cross-user access in an approved isolated setup. No offline record export or sync has been implemented by this plan.

The experimental offline panel loads only manually supplied local snapshots in memory; it does not authenticate the file or current user and cannot preserve permissions by itself. The ZIP still contains no records; current online graph/geography/structures depend on Frappe. Authorized export, editing, synchronization and conflict detection remain unimplemented. Record export remains blocked on the security design and real role/field/link behavior described above.

The new candidate collector uses current-session list/document read and export checks and filters both relationship endpoints, but is non-whitelisted and not connected to the viewer. Its server-only HMAC envelope does not authenticate an offline user or encrypt contents. See `offline-snapshot-security.md`; no real record export has been performed or authorized.

An experimental v3 P-256 issuer and viewer verification path now connects the candidate collector to a separately provisioned trust policy, using synthetic tests only. There is no default policy, public export endpoint, encryption, trustworthy offline identity or actual revocation service. Unsigned v1 files remain clearly unverified. No real records have been exported; see `signed-snapshot-prototype.md`.
